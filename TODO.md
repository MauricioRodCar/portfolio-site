**1. Maze / pathfinding algorithm visualizer — done, branch `feature-maze-visualizer`.** New `#puzzle` section placed right after Hero, before case studies (strongest hook for non-technical visitors — proves the hero tagline interactively before they read anything else). Visitor draws walls on a grid, and an A* search animates the exploration (cyan-tinted) and final path (solid cyan) live. Styled as a terminal-window card (`solver.ts`), no heavy deps — `src/components/maze/astar.ts` (plain algorithm) + `MazeVisualizer.tsx` (client component).
- **Algorithm: A\*** (Mauricio's pick over BFS — flashier, heuristic-driven, explores fewer cells).
- **Start/end points: draggable**, implemented as plain pointer events (no drag-and-drop library). Mauricio asked directly whether this risks performance — it doesn't: A* over a grid this size (14×22 = 308 cells) runs in well under a millisecond, so raw compute was never the concern. What actually shipped: a **150ms debounced `useEffect`** keyed on `[walls, start, end]` re-solves once the visitor stops interacting, rather than the pointerup-triggered approach originally sketched — simpler to reason about and covers both wall-drawing and marker-dragging with one mechanism.
- **Touch/mobile dragging required rethinking cell hit-testing.** Per-cell `onPointerEnter` (the naive approach) doesn't work on touch: touch input gets implicit pointer capture on whatever element received the initial `touchstart`, so sibling cells never fire `pointerenter` during a drag — mouse-only bug that wouldn't have shown up without explicit touch-viewport testing. Fixed by moving hit-testing to the grid container: a single `onPointerMove` uses `document.elementFromPoint()` + `data-row`/`data-col` attributes to resolve the cell under the pointer, identical code path for mouse and touch, plus `setPointerCapture` on the container so it keeps receiving events regardless of what's visually under the finger.
- **Real bug found and fixed via Playwright (not caught by lint/build):** the animated-exploration step function's `setVisited(prev => ...)` updater closed over a mutable outer `i` (incremented right after the `setVisited` call) instead of capturing the current cell by value. This crashed the whole page on load — `Cannot read properties of undefined (reading 'row')` — because React's dev/Strict-Mode double-invocation of state updater functions (to detect impure reducers) re-ran the closure after `i` had already advanced, indexing past the end of the array. Production builds don't double-invoke, so this would have been invisible in a prod-only smoke test; caught because Playwright testing was run against the dev server first. Fixed by snapshotting the cell (`const cellKey = pointKey(visitedOrder[i])`) *before* constructing the updater, making it pure regardless of how many times React calls it.
- Verified with Playwright: desktop mouse (draw wall, drag start marker, reset), mobile touch viewport (390×844, drag-drawn wall, no horizontal overflow), both locales, zero console errors. Lighthouse unaffected: desktop 100/100/100/100\*, mobile 95/100/100/100\* (\*SEO's local 91 is the same known localhost-canonical artifact from Phase 4, not a real regression).

- **Playground implementation: CodeMirror + sandboxed runtime, not Sandpack.** The brief (section 4) lists both as acceptable. Sandpack ships a full in-browser bundler, which is much heavier than this use case needs — the playground only has to run a small, self-contained tool-calling function against editable input and print a string, not resolve imports or render a live DOM preview. `@uiw/react-codemirror` gives the same "real editable code with real syntax highlighting" feel at a fraction of the weight, which matters given the explicit performance budget (section 3: Lighthouse ≥ 90) and the requirement that the playground not hurt the rest of the site's performance. The edited code runs via `new Function(...)` entirely in the visitor's own browser tab — same trust boundary as a devtools console, no server involved, standard for this kind of in-browser code playground.
- **Nav overflow on narrow mobile:** with 3 section links + locale switcher + Contact button, the nav no longer fit below ~480px wide. Fixed by hiding the section links (`How I Think` / `Playground` / `Stack`) below the `md` breakpoint, keeping brand + locale switcher + Contact always visible — no hamburger menu, since the single-page site is still fully reachable by scrolling and section 7 only calls for "functional," not pixel-perfect, mobile.
- **`SITE_URL` hardcoded in `[locale]/layout.tsx`:** used for `metadataBase`, canonical/hreflang, and Open Graph `url`. Currently `https://portfolio-site-omega-ivory.vercel.app`. **Update this if/when Phase 5 adds a custom domain** — social previews, canonical tags, and the Audit section's `pageSpeedUrl`/`liveUrl` (`src/content/audit.ts`) all depend on it being correct.
